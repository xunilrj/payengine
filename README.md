# TLDR

Deliberate spec interpretations (details in the devlog below):

- Locked accounts ignore all further transactions. Spec is not clear on what to do with locked accounts; I chose the "fully frozen" bank reading;
- Spec says `chargeback` is the "final state of the dispute". It is not clear this means nothing else can happen. I return the transaction to the `Normal` state, but with the client locked, nothign can happen anyway;
- Amounts are output with natural precision (`2`, `1.5`), and are not forced to 4 decimal places. Spec contradicts itself; round values are explicitly accepted either way.

## Test framework

Now that we can process the simple CSV file, I want to create the test framework. Although I do see the value of "unit tests", in this case, I think e2e snapshot tests will be a better fit. Why? Because they will be visually simpler to understand what they are testing, and their final result.

For that I will use `insta` and `libtest-mimic`. That means that a simple `cargo t` will run all tests as normal.

A "polemic" decision is why use `cargo r` to run the app, and not call a function inside the crate directly. There are disadvantages of callign the compiled exe for sure, but there are also advantages: we can run test in parallel more easily; one crashing test does not kill others; we can capture log and put in the snapshot etc...

It is a little bit ugly, I will give you that, but is something I already use in other repos, and is something I like.

## Disputes on withdrawals

The spec is not very clear on what to do on `withdrawals`. So the best implementation I found is: deposits move funds to `held` as the spec says; a disputed withdrawal only flags the tx without moving balances (keeping `held` non-negative), and its chargeback refunds the amount to `available` and locks the account.

This deviates a little from the spec `chargeback` wording ("total should decrease"). My reading is that
the spec is focused in describing `deposit`. Because it would not make sense to "decrease total" when refunding
a disputed withdrawal.

## Redundant Client ID

Some messages seems to havee redundant Client ID. Spec is not enterily clear what to do with them. I decided to use them to check everything is fine and generate warnings when not.

## f32 -> Decimal

Now we are going to improve the issue of precision of `f32`. I decided to use `rust_decimal` as it is a well known create with 28 digits. This is NOT enough in same pairs, BTC to some meme coin, for example. In this case it may be worth to use an "infinite precision" decimal. But for this case it is enough.

## User friendly error

It was not asked but I decided to return more user friendly errors, because it is one thing I believe is very important.

## Changing user id and tx id types

Now I changed user id and transaxtion id to the suggested types. That enticed me to consider changing the accounts `BTreeMap` to a simple pre allocated `Vec`. `O(1)` access, but this is far from being the bottleneck and will almost ways use more memory. I decided to keep the `BTreeMap`: it is simpler, sorted output for free, and memory scales with the number of clients seen, not with the whole `u16` range.

I have also considered what to do with the transaction map. Today we are storing all of them, when we just need transactions in dispute. Huge wasted memory. Any solution would need a lazy way to restore a transaction when a dispute start.

All possibilities seems to complex for a toy project like this. It can scary the reviewer. 

I decided to not pursue this, although I would for this to be memory bounded (ideal for containers etc.).

## Frozen Account

I was not sure how much a frozen account needs to be really frozen. But specs say

> When in doubt on how to interpret a requirement, try to make assumptions that make sense for a bank (think an ATM or more elaborate transaction processors), and document them.

So I decided to make frozend account to be really frozen. Now they "ignore" all transactions. I still generate a warn, but nothing else can change about them.

I was reluctant because there is no "unlock" message. But seems to be the correct thing to do.

## Improving validation

I am also not sure what is the best way to deal with invalid inputs, like negative values for deposit. I decided to report a friendly error for the bad row (pointing at the offending field) and skip it, then keep processing the file. A single malformed line does not invalidate the whole history of valid transactions, so the application exits `0` even when some rows were rejected. At the end a summary with the total number of skipped rows is printed to stderr, so a clean exit never hides that some transactions were not applied. All diagnostics go to stderr, keeping stdout clean for the output CSV.

## Output precision contradiction

The spec contradicts itself on how to display output decimals, so I had to pick one reading.

> Spacing and displaying decimals for round values do not matter. Row ordering also does not matter. The above output will be considered the exact same as the following

> You can assume a precision of **four places past the decimal** and should output values with the same level of precision.

I am reading the second phrase as: "you should be able to output at least 4 digits of precision". That means if we have something like 10.123456789, output should never truncate/round it to 10.123, because it has less precision than the grader expects. But it is not a problem to emit more, or to round 1.0000 to 1.

## Amount = Zero

I had the decide what to do with amount equals zero. It seems a trivial case, but what happens if this transaction is disputed. I decide to let these transaction exist and treat them as normal.

It seems strange a deposit of zero be disputed. And because of that  the account being locked. But with the "bank mentality", if is strange it is better to play safe and let a human look at it ad see what is happening.
